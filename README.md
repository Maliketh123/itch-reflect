# itch-reflect

A decoder for NASDAQ ITCH 5.0 market data, written twice in C++:

- **by hand**: one decoding function per message type, with every byte offset written out;
- **by C++26 reflection**: one generic `decode<T>` that the compiler turns into a decoder for any message struct.

The project measures whether the generated decoder is as correct and as fast as the hand-written one, on real NASDAQ data.

## Results

All three measurements say the two decoders are the same.

| Check | Hand-written | Generated by reflection |
|---|---|---|
| Messages decoded (real feed, 2.1 GB) | 64,904,600 | 64,904,600 |
| Checksum over all decoded fields | 17380614335067787380 | 17380614335067787380 |
| Fastest of 5 passes | 285.76 ms | 285.80 ms |
| Median of 5 passes | 286.43 ms | 286.08 ms |
| Time per decoded message | 4.40 ns | 4.40 ns |
| Machine code for `AddOrder` (`-O3`) | 49 lines of assembly | the same 49 lines, except two one-byte loads (see below) |

1. **Correctness.** On 64.9 million real messages, both decoders produce the same checksum over every numeric field.
2. **Speed.** The two are within 0.02% of each other in this run, and within 0.3% across all runs, with the faster one changing between runs. These gaps are measurement noise. The generated decoder always runs second within each round, which may also contribute.
3. **Machine code.** GCC emits the same instructions for `decode<AddOrder>` as for the hand-written `decode_add_order`, apart from the two one-byte `char` fields: the hand-written decoder loads them with `ldrsb` (sign-extending) and the generated one with `ldrb` (zero-extending). Both values are then stored with `strb`, which keeps only the low 8 bits, so the bytes written are the same. Before the change below, the two functions were identical instruction for instruction (68 lines each).

Reflection does all its work while compiling. By the time the program runs, only ordinary decoding code is left, which is why the speed and the machine code match.

## Improvement: reading whole fields

The first version of `read_be` built each number one byte at a time: one load, one shift and one add per byte. For 4- and 8-byte fields the compiler did not recognise this as a byte-order reversal, so an 8-byte field took about 22 instructions.

`read_be` now copies the whole field into a 64-bit integer with `std::memcpy`, reverses its bytes with `std::byteswap`, and shifts out the unused bytes. On arm64 this becomes one load and one `rev` instruction per field. The old loop is kept for compile-time evaluation, selected with `if consteval`, because `std::memcpy` cannot run at compile time.

| | Byte-by-byte | Whole field + byte swap |
|---|---|---|
| Assembly lines for `AddOrder` | 68 | 49 |
| Byte-swap instructions | 2 (`rev16`) | 6 (one per multi-byte field) |
| Hand-written, fastest pass | 315.61 ms | 285.76 ms (9.5% faster) |
| Generated, fastest pass | 316.44 ms | 285.80 ms (9.7% faster) |
| Checksum | 17380614335067787380 | 17380614335067787380 |

Both decoders call `read_be`, so both gain equally. The overall gain is smaller than the reduction in decoding instructions because the timed loop also walks the length framing and adds up the checksum.

## How it works

Each message is a plain struct. The only addition is a note on fields whose width on the wire differs from the size of their C++ type:

```cpp
struct AddOrder {
    char message_type;
    std::uint16_t stock_locate;
    std::uint16_t tracking_number;
    [[= Wire{6}]] std::uint64_t timestamp;   // 6 bytes on the wire, stored in 8
    std::uint64_t order_reference;
    char side;
    std::uint32_t shares;
    std::array<char, 8> stock;
    std::uint32_t price;
};
```

`decode<T>` walks the members of `T` at compile time with `template for`. For each member it finds the wire width (the `Wire` annotation if present, otherwise the size of the type), reads that many big-endian bytes into the member through a splice (`obj.[:m:]`), and moves forward. The `std::array<char, 8>` symbol is copied byte by byte; the choice is made with `if constexpr`.

| | Hand-written | Reflection |
|---|---|---|
| Decoding code for the 5 message types | 5 functions, 61 lines | 1 function template, 26 lines |
| Adding a new message type | write a new function, offsets by hand | write the struct only |

## Messages covered

| Type | Message | Bytes |
|---|---|---|
| `A` | Add Order | 36 |
| `E` | Order Executed | 31 |
| `X` | Order Cancel | 23 |
| `D` | Order Delete | 19 |
| `U` | Order Replace | 35 |

Other message types are counted and skipped.

## Layout

| Path | Contents |
|---|---|
| `src/bytes.hpp` | `read_be<T, N>`: reads an N-byte big-endian number |

| `src/reflect_decode.hpp` | `decode<T>`, generated by reflection |

| `tools/asm_compare.cpp` | the two `AddOrder` decoders, for comparing machine code |

## Building

Needs GCC 16 or later (reflection is enabled with `-freflection`) and CMake.

```
cmake -S . -B build -DCMAKE_CXX_COMPILER=g++-16
cmake --build build
```

Run the tests:

```
./build/test_bytes
./build/test_itch
./build/test_reader
./build/test_reflect_decode
./build/test_reflect_itch
```

## Reproducing the results

**Data.** NASDAQ publishes sample feed files at `https://emi.nasdaq.com/ITCH/`. The results above use the BX exchange file for 30 January 2019:

```
curl -L -o data/20190130.BX_ITCH_50.gz "https://emi.nasdaq.com/ITCH/Nasdaq%20BX%20ITCH/20190130.BX_ITCH_50.gz"
gzip -dc data/20190130.BX_ITCH_50.gz > data/20190130.BX_ITCH_50
```

**Speed and correctness.**

```
./build/bench data/20190130.BX_ITCH_50
```

**Machine code.**

```
g++-16 -std=c++26 -freflection -O3 -S -I src tools/asm_compare.cpp -o asm_compare.s
awk '/^_hand_add_order:/,/^[ \t]+ret/' asm_compare.s | tail -n +2 | grep -v '^L' > hand.s
awk '/^_gen_add_order:/,/^[ \t]+ret/'  asm_compare.s | tail -n +2 | grep -v '^L' > gen.s
diff hand.s gen.s && echo IDENTICAL
```

The `awk` patterns assume macOS symbol names (a leading underscore).

## Setup used

- Apple Silicon Mac (arm64)
- GCC 16.2.0 from Homebrew, `-O3` (CMake Release build)
- Whole feed file held in memory; each decoder run 5 times, alternating

## Limitations

- One machine and one compiler. Results may differ on x86 or with Clang.
- About two-thirds of one trading day: the 2,128,871,424-byte file is the readable part of a download damaged partway through.
- The timed loop includes walking the length framing and adding up the checksum, not only the decode calls.
- Timings are from a laptop under normal conditions, with warm caches after the first pass.
- Machine code was compared for `AddOrder` only.
- `decode<T>` relies on every member being written; a member it skips would be left uninitialised.
- Supported member types: `char`, unsigned integers up to 64 bits, and `std::array<char, 8>`.
- The fast path of `read_be` assumes a little-endian machine; a `static_assert` stops the build otherwise.
